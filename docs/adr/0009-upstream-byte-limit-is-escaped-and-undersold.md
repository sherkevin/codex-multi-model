# 0009. 上游字节硬顶按「ASCII 转义后」计量，且宣称值不可信

- 状态：Accepted
- 日期：2026-09-13
- 相关文件：`codex-model-router.py`（`_body_bytes` / `_limits_for` / TooLarge 卸载循环）、
  `probe-body-byte-limit.py`
- 关联：[0004](0004-byte-limit-vs-token-limit.md)（字节超限不是 token 超限）

## 背景

用户再次报同一个错误，而这次日志里出现了自相矛盾的证据：

```
[body] 上游 TooLarge：就地卸载 4,759,018 B → 4,586,879 B，重试第 4 次
失败 HTTP 400 ... "Exceeded limit on max bytes to request body : 6291456"
```

卸载到 4,586,879 B，只有宣称硬顶 6,291,456 B 的 73%，上游却仍然说超限。
0004 已经把字节超限和 token 超限分开、也做了闭环预检，为什么还会这样？

从日志反推先得到一组矛盾数据：同一线程里 4,671,315 B 的请求**成功**过，
4,759,018 B 的**被拒**。纯字节阈值解释不了——除非我们量的字节和上游量的字节
不是一回事。

## 实测

二分实测（同一网关、同一模型，只改填充内容的中英比例，每点 6 轮收敛）：

| 非 ASCII 字符占比 | 实测可通过的**发送**字节 | 换算成**转义**字节 | vs 4,718,592 |
|---|---|---|---|
| 0.000 | 4,717,472 | 4,717,472 | -0.0% |
| 0.125 | 3,647,460 | 4,741,698 | +0.5% |
| 0.250 | 3,200,442 | 4,800,663 | +1.7% |
| 0.500 | 2,676,820 | 4,684,435 | -0.7% |
| 1.000 | 2,327,860 | 4,655,720 | -1.3% |

两个结论同时从这组数据里出来：

1. **计量口径是 ASCII 转义后的字节，不是我们发出的 UTF-8 字节。**
   发送字节的阈值随中文比例一路下滑，纯中文时只剩 ASCII 的一半（比值 0.478）；
   换算成转义字节后五点全部收敛到同一常数的 ±1.7% 内。机制是中文每字符
   UTF-8 占 3 B、转义成 `\uXXXX` 占 6 B。
2. **真实硬顶是 4,718,592 B（= 4.5 MiB），不是错误消息里的 6,291,456 B。**
   后者是外层网关的数，真正卡住请求的是模型层，比宣称值小 25%。

顺带纠正 0004 里的一处判断：把 `call_upstream` 改成 `ensure_ascii=False`
「让中文体积减半、是最便宜的一击」——这对**带宽**成立，对**上游的字节校验**不成立。
我们少发了一半字节，上游算的还是转义后的全量。发送端保持 `ensure_ascii=False`
是对的（省带宽、上游也接受），错的是拿它当预算口径。

## 决策

1. `_body_bytes()` 量 **`ensure_ascii=True`** 的字节数，与上游校验口径一致。
   纯 ASCII 内容（含 base64 图片）两种口径同值，所以英文会话和图片完全不受影响；
   只有中文等非 ASCII 内容会被正确计入。
2. `UPSTREAM_BODY_BYTE_LIMIT` 默认值改为实测的 `4718592`。宣称值一律不信，
   换网关必须用 `probe-body-byte-limit.py` 重新实测。
3. **卸载轮数与重试次数解耦。** 旧实现共用 `for attempt in range(1, MAX_RETRY+1)`，
   最后一轮 `continue` 直接掉出循环——那个已经卸载到够小的 payload **从未发出**，
   请求照样失败（就是上面 4,586,879 B 那次）。现在 `attempt`（瞬时错误退避）与
   `offload`（字节卸载）是两个独立计数器，卸载后必然再发一次。
4. **每轮卸载跑完整链路并收紧预算。** 旧实现每轮只走一步（丢一张图或截一条文本），
   要靠多轮才收敛，而轮数又被重试计数吃掉。现在每轮调
   `_enforce_body_byte_limit`（降档 → 丢最旧图 → 截最长文本），并把预算再乘
   `BODY_OFFLOAD_DECAY`（默认 0.88），正常一轮就收敛。

## 影响

- 默认预算从 5,788,139 B（真实上限的 **123%**）降到 4,341,104 B（92%）。
  旧预算高于真实上限，意味着每个多图请求都必然先被上游拒一次、再靠烧重试轮卸载。
- 中文会话收益最大：旧口径把中文体积低估近一倍，预检形同虚设。
- 模拟上游闭环验证（限额 1.5 MB、按转义口径）：构造 sent=3.0 MB / escaped=6.0 MB
  的中文请求，预检压到 3.75 MB，上游一次成功；再把预检预算故意设成高于模拟限额，
  则第一轮被拒、卸载一轮后成功——正是旧代码会失败的那条路径。
- 新增 `probe-body-byte-limit.py`：同时判定**口径**与**阈值**，直接输出可抄进
  `router-routes.json` 的 `body_byte_limit`。用模拟上游自测，口径判定正确
  （比值 0.478）、阈值误差 1.6%。
- 启动日志明确写出口径，避免下次再把 `body<=N B` 读成发送体积。
